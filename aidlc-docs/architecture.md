# roblox-map 아키텍처와 대규모 맵 최적화

작성 2026-10-14. 실제 동네를 Roblox 맵으로 만드는 이 프로젝트의 구조, 규칙, 그리고 맵이 커질 때의 최적화 방안을 한곳에 정리한다. 새 기능(유닛)을 시작하기 전에 이 문서와 맞는지 본다. 바꿀 때는 아래 "결정 기록"에 남긴다.

---

## 1. 큰 그림: 층을 나눈 파이프라인

데이터가 한 방향으로만 흐른다. 각 층은 바로 앞 층의 결과만 읽는다.

```
원본               중간 저장소          사람·Claude 판단         생성 규칙              엔진 반영             게임
OSM, V-World  →   data/map.db    →   regions/<구역>/      →  src/layout*.py    →   build_luau.py    →   Studio Workspace
거리뷰, 위성        (SQLite, 로컬)       cells/<칸>/*.json (git)  streets.py (테스트)    덩어리·chunks.json     + 게임 스크립트
```

| 층 | 무엇을 하나 | 바뀌면 |
|---|---|---|
| 원본 수집 | `cells.py`, `register.py`, `capture.py`, 위성 타일 | 다시 받으면 된다(로컬) |
| 판단·보정 | 눈가림 판단, 세부 판단, 보정, 위성 나무, 간판 자산 ID | **git에 남는 사람의 결정**. 잃으면 다시 판단해야 한다 |
| 생성 규칙 | 외곽선 → 박스, 창·지붕·간판·가로·나무·(U7) 내부 | 규칙을 고치고 다시 생성. 같은 입력이면 같은 결과(결정적) |
| 엔진 반영 | Luau 덩어리 → `Builder`가 부품만 만든다 | 계산은 하지 않는다 |
| 게임 | 미니맵, 킥보드 등 | 맵 부품을 고치지 않고 읽기만 한다 |

원칙
- **계산은 Python, Studio는 부품만**: 좌표·모양 계산은 테스트할 수 있는 Python에 둔다.
- **결정적 생성**: 무작위는 `details_rules.pick`(crc32)만. 언제든 다시 만들어도 같은 맵.
- **다시 만들 수 있는 것과 없는 것을 나눈다**: 다시 만들 수 있는 것(원본, DB, 덩어리 파일)은 로컬, 사람의 결정은 git.

## 2. 자동 생성과 손작업

| | 자동(`Workspace/Auto/<칸ID>`) | 손작업(`Workspace/Manual/<이름>`) |
|---|---|---|
| 만드는 것 | 모든 건물·도로·가로·나무 | 학교, 부흥중, 공원처럼 데이터로 안 되는 곳 |
| 다시 만들기 | 칸 폴더를 비우고 다시 | 맨 위 폴더가 없을 때만 만든다(지우지 않음) |
| 겹칠 때 | 손작업에 `BuildingId`가 있으면 자동이 그 건물을 건너뛴다 | 손작업이 이긴다 |

규칙
- 손작업은 **바뀌지 않는 기준**(건물 ID, 외곽선에서 계산한 기준점)에 붙인다. 자동 박스의 번호·좌표를 숫자로 적지 않는다(U7에서 `src/anchors.py` → `studio/anchors.json`로 바꾼다. 지금은 부흥중 지붕이 어긋나 있다).
- 공통으로 고칠 문제는 규칙으로, 한 건물만의 문제는 보정(`overrides`)이나 손작업으로.

## 6. 대규모 맵 최적화 방안

맵이 커질 때 비용은 크게 다섯 가지다: **그리기(부품·재질·투명·그림자), 물리(충돌), 메모리(인스턴스 수), 네트워크(복제), 편집(Studio)**. 방안을 비용이 싼 것부터 적는다.

### 6.1 지금 바로 싸게 지킬 것 (이미 일부 적용)

| 방안 | 효과 | 이 프로젝트 |
|---|---|---|
| 장식 부품의 충돌 끄기(`CanCollide/CanTouch/CanQuery = false`) | 물리 계산·충돌 검사 감소 | 창·간판·장식(`facade`, `sign`)은 이미 꺼져 있다 |
| 작은 부품 그림자 끄기(`CastShadow = false`) | 그림자 그리기 감소 | 장식은 꺼져 있다 |
| 모든 맵 부품 `Anchored`, 실행 중 속성 안 바꾸기 | 엔진이 정적 부품을 묶어 그린다 | 그렇다 |
| 재질·색 종류 줄이기 | 재질 전환 감소 | 팔레트 표로 제한 |
| 투명 부품 최소화 | 정렬·겹쳐 그리기 비용 | 유리는 불투명 판으로 |
| 간판 글자 `MaxDistance` | 먼 SurfaceGui를 그리지 않는다 | 200~300 stud |
| 부품 하나로 될 것을 여러 개로 쪼개지 않기 | 인스턴스 수 | 규칙에 예산 테스트(P5-15) |

### 6.2 스트리밍 (U7에서 켬)

- `Workspace.StreamingEnabled = true`: 서버는 다 가지고, 플레이어에게는 가까운 부분만 보낸다. 메모리·그리기·접속 시간이 함께 준다.
- 값: `StreamingTargetRadius` 512 stud(약 140 m), `StreamingMinRadius` 128, `StreamOutBehavior = Opportunistic`(멀어진 것을 내린다).
- 건물을 `Model`로 묶고 `ModelStreamingMode`를 정한다: 건물 하나는 통째로(`Atomic`) 오고 가게 해서 반쪽만 보이는 일을 막는다. 스폰 주변·랜드마크는 `Persistent`.
- 먼 경치: `Model.LevelOfDetail = StreamingMesh`를 켜면 스트리밍 반경 밖의 건물이 간단한 대리 메시로 보인다. 도시 스카이라인이 비지 않는다.
- 주의: 클라이언트 스크립트(미니맵 등)는 멀리 있는 부품이 없을 수 있다고 가정한다. 맵 정보가 필요하면 부품을 찾지 말고 데이터(예: `minimap.py`가 만든 표)를 쓴다.

### 6.3 거리별 상세도 (LOD)

| 거리 | 보이는 것 |
|---|---|
| 가까이(건물 안·앞, 약 60 m) | 전부: 내부, 간판 글자, 작은 가로시설 |
| 중간(약 60~140 m) | 외관(창, 지붕, 띠), 큰 간판 |
| 멀리(스트리밍 밖) | 대리 메시(StreamingMesh) 또는 단순 박스 |

구현 방법
- 내부와 작은 장식은 별도 `Model`(예: `Interiors/<건물>`)로 묶어 스트리밍 반경을 더 짧게 쓰거나, 플레이어가 건물에 들어갈 때만 보이게 한다.
- SurfaceGui·조명은 `MaxDistance`·`Range`로 거리 제한.

### 6.4 반복 부품을 키트(모델)로

- 창틀, 문, 가구, 가로등, 나무처럼 **같은 모양이 수천 번 반복**되는 것은 표준 모델을 만들어 복제한다. 같은 메시(MeshPart)를 여러 번 쓰면 엔진이 한 번에 그린다(인스턴싱). 모양을 바꿀 때도 키트 하나만 고친다.
- 이 프로젝트에서 효과가 큰 순서: 나무(지금 4부품 → 메시 1), 가구(U7), 가로등·전봇대, 창+창틀.
- 대가: 메시는 Roblox에 올려야 하고 검수를 받는다(간판 때 계정 검수 경험). 올리기 전에 내용 점검, 한 번 올리면 자산 ID를 git에 고정(간판과 같은 방식).

### 6.5 건물을 메시 하나로 합치기 (필요해지면)

- 건물마다 수십~수백 부품을 메시 하나(또는 몇 개)로 합치면 인스턴스 수가 크게 준다. 대규모 도시 맵의 일반적인 마지막 단계다.
- 방법: Python이 외곽선·층·창으로 메시를 만들어 올리거나, Studio의 EditableMesh로 만들어 저장한다(저장·게시 방식은 시험 필요).
- 대가: 업로드·검수, 고칠 때마다 다시 올리기, 부품 단위 편집이 어려워짐. **칸이 10개를 넘거나 FPS 예산을 못 지킬 때** 검토한다.

### 6.6 지면과 나무

- 땅은 칸마다 큰 판 하나(지금). Terrain은 쓰지 않는다(도시 평지, 부품 판이 싸고 결정적).
- 나무는 위성에서 읽은 위치에 둔다. 많아지면 키트(6.4)로.

### 6.7 네트워크와 스크립트

- 맵 부품마다 스크립트를 넣지 않는다. 기능은 `CollectionService` 태그나 속성을 단 부품을 스크립트 하나가 찾아 처리한다.
- 서버가 확인할 것은 서버에서(킥보드 속도). 클라이언트가 보낸 값은 믿지 않는다.
- 실행 중 맵 부품을 대량으로 바꾸지 않는다(복제 폭주).

### 6.8 편집(Studio)과 생성 속도

- 생성은 덩어리(70 항목) 단위, 덩어리마다 `task.wait()`. 덩어리 시간을 기록한다.
- 칸 폴더 단위로만 비우고 다시 만든다.
- 장소가 무거워지면 칸별로 숨겨 두고 편집하거나, 동네별 장소로 나눈다(3절).

### 6.9 장소 나누기 (가장 큰 규모)

- 한 장소에 다 넣기 어려워지면 동네(또는 구역)별 장소를 만들고 경계에서 TeleportService로 넘긴다. 플레이어 데이터는 DataStore로 넘긴다.
- 언제: 동네가 여럿이 되거나, 스트리밍을 켜도 편집·서버 메모리가 한계에 가까울 때.

| 2 | 스트리밍 켜기, 건물을 Model로, 랜드마크 Persistent | U7 |

## 7. 측정 방법

- 걷기 FPS: Play → `RenderStepped` 기록(평균, 1초 최저, 가장 느린 프레임). **Studio 창이 앞에 있어야 한다**(뒤에 있으면 15 FPS 고정).
- 부품 수: 칸 폴더의 자손 수, 매니페스트의 `items_*`.
- 세부: Studio의 MicroProfiler(Ctrl+F6), 개발자 콘솔(F9)의 메모리·네트워크, 렌더 통계(Shift+F2).
- 휴대폰: Studio 기기 에뮬레이터는 화면 크기만 흉내 내므로 실제 성능은 실제 휴대폰으로 한 번씩.
- 결과는 `aidlc-docs/construction/build-and-test/performance-test-instructions.md`에 남긴다.

## 8. 작업 흐름

- 기능(유닛)마다 AI-DLC: 질문 파일 → 요구 → 설계 → 계획 → 코드·테스트 → Studio 확인. 결정은 `CLAUDE.md` 결정 사항과 `aidlc-docs/audit.md`에.
- **세션**: 동시에 하나만, 칸 하나에 세션 하나, 세션마다 인지 → 메모리 → 구현 → 검증 → 기록(CLAUDE.md "세션 흐름", 사용자 결정 2026-10-14). 개발 중 알게 된 것은 `aidlc-docs/lessons.md`. 커밋은 자기 파일만.
- 큰 Studio 작업 전 `.rbxl` 복사본(사용자), 끝나면 Roblox에 저장.

## 9. 결정 기록과 남은 결정

정해진 것: 1~2절의 원칙, H3 칸, 계산은 Python, 결정적 생성, Auto/Manual, 외곽선 따르는 박스(U7), 내부 있음·스트리밍 켜기(U7 Q6~Q8).

남은 결정
- 키트·메시를 언제 도입할지(6.4, 6.5)와 메시 업로드 검수 대책
- 휴대폰 목표 기기와 FPS
- 두 번째 동네의 시작 시점과 `regions/` 구조
- Rojo 도입 여부(4절 폴더 정리 뒤)
