# Performance Test Instructions

부하 시험은 해당 없다(단일 사용자, 칸 단위 배치 실행). 대신 NFR-P1("칸 하나를 수 분 이내")을 실제 칸으로 잰다.

## 요구
- **칸 하나 수집·조립**: 수 분 이내(U1-NFR-P1).
- **DB 크기**: 3칸 규모에서 문제되지 않을 것.

## 측정 방법
```bash
time uv run --env-file .env src/cells.py --cells <칸ID>
time uv run --env-file .env src/register.py --cells <칸ID>
ls -la data/map.db
```
`collection_runs`의 `started_at`, `finished_at`으로도 볼 수 있다.

## U3 거리뷰 캡처 (2026-10-13, 첫 칸 `8930e0af13bffff`)

### 요구
- 새 파노라마 100장(실행당 상한)을 받는 데 10분 이내(U3-NFR-P1). 크롭은 장당 1초 이내.
- 호출 간격 1초(설정값)를 지킨다.

### 측정
| 실행 | 소요 | 내용 |
|---|---|---|
| 1차 | 8분 49초 | 계획(건물 122개, 약 6분 20초) + 파노라마 100장과 크롭 116개(약 2분 30초) |
| 2차 | 2분 31초 | 파노라마 100장, 크롭 183개 |
| 3차 | 약 1분 | 파노라마 26장, 크롭 64개 |
| 4차(재실행) | 1초 | 할 일 없음 |

| 항목 | 결과 | 요구 | 판정 |
|---|---|---|---|
| 파노라마 100장 내려받기와 크롭 | 약 2분 30초(장당 약 1.5초) | 10분 이내 | 통과 |
| 크롭 한 장 | 약 0.13초(`render_crop`) | 1초 이내 | 통과 |
| 건물 한 채 계획(후보 조회 + 새 메타데이터) | 평균 약 3.1초 | - | 병목 |
| 첫 칸 전체 | 약 13분 | - | - |
| 저장량 | 파노라마 226장 319 MB(평균 1.41 MB), 크롭 363개 65 MB(평균 178 KB), 합 384 MB | 한도 없음(Q4=A), 보고 | 보고 |
| 네이버 반응 | 차단 신호 0, 재시도 0, 실패 0 | 차단 없이 | 통과 |

- 호출 간격 1초로 충분했다. 파노라마 한 장은 타일 24개 요청을 면 단위로 4개씩 동시에 받는다(라이브러리 동작). 합쳐 약 6,000개 요청을 약 13분에 보냈고 차단되지 않았다.
- 병목은 계획 단계다(건물마다 조회 1번 + 처음 보는 파노라마마다 메타데이터 1번, 각각 호출 간격 1초). 칸이 늘면 이웃 칸과 겹치는 파노라마는 이미 있어서 줄어든다.
- 세 칸 합계 저장량은 약 1.1 GB 이하로 예상한다(칸 경계 파노라마는 공유).
- 규칙을 바꾼 뒤 크롭 360개를 다시 만드는 데 73초(장당 약 0.2초, 파일 쓰기 포함). 네이버 호출 없음.
