# 정면 트레이싱 실험: 사진을 정면에 펼쳐 조각을 따라 만들기 (2026-10-17)

다른 세션(캡처 파일 `captures/`와 Studio가 있는 Mac)에 전달해서 실험하는 문서다. 결과가 좋으면 유닛(U9)으로 세워 1급 칸의 기본 생성 방식으로 넣는다. 그 전에는 지금 사이클(7필드 판단 → 규칙 생성)을 바꾸지 않는다.

## 1. 배경 (사용자 입력 2026-10-17)

- 사용자: "거리뷰 이미지 수집하잖아. 지금 결과물도 괜찮지만 수집한 자료 질에 비해 결과는 좀 아쉬움." → "내가 건물을 보고 특징만 기억을 해서 너한테 말하고 만들라 하면 똑같이 만들 수 있겠어?" → "어릴 때 그림 따라 그릴 때는 흰 종이 아래에 그림을 깔고 따라 그렸거든. 그런 식으로 건물 사진 자르고 → 자른 조각들로 따라 만드는 식은 안 되나?"
- 진단: 지금 흐름은 사진 → 객관식 7필드(`details`: 마감 6·1층 3·계단실 4·돌출창 0/1·발코니 0/1·지붕색 6·옥상 4) + 메모 → 규칙이 **상수 위치**로 생성(`layout_details.front_items`: 계단탑 정면 왼쪽 1/3, 돌출창 오른쪽 1/3, 발코니 전 층 같은 폭, 창은 면 길이 ÷ 간격, 틀 색은 해시). 사진을 본 쪽(판단 에이전트)은 그리지 않고, 그리는 쪽(규칙)은 사진을 못 본다. 82칸 7,532동 메모에 shutter 455·awning 501·fence/gate 334·granite/bands 556·curved/arched/round 425동이 적혀 있지만 생성기는 열 단어만 읽는다. 6d3 G3는 3회 수정 뒤에도 실패 0.43이고 남은 실패는 전부 "지도가 표현할 수 없음"(창 50·돌출물 51·1층 49·지붕 45동)이었다.
- 바꾸는 것은 가운데 한 단계뿐이다: 사진을 보고 **체크**하는 대신, 사진을 **정면에 펼쳐 놓고 위치와 크기를 재서** 적는다. 박스(V-World)·카메라(크롭)·부품 생성(`_wall_part`)은 그대로 쓴다.

## 2. 원리

크롭 한 장마다 카메라가 숫자로 있다(`estimate.py plan` → `data/build/<칸>/review.json`의 `camera.position`·`camera.look_at`·`crop_fov_h_deg`, Studio 좌표·stud). 크롭은 `projection.render_crop`이 큐브맵에서 핀홀로 그린 그림이라 렌즈 왜곡이 없다. 건물 박스는 `chunks.json`의 `k=building` 항목(G3 `lookalike.building_parts`가 쓰는 것)으로 있다. 그러면

1. 박스의 정면(카메라를 향한 면 중 투영 넓이가 가장 큰 면) 네 모서리를 사진 픽셀로 투영할 수 있다(`lookalike.Camera.to_px`, 윤곽선 그리는 계산 그대로).
2. 그 네 점과 "면 위 좌표(가로 u m, 높이 y m)" 사이의 호모그래피(3×3)로 사진을 **정면 평면에 펼친다**: 가로 축 = 면을 따라 0~L m, 세로 축 = 바닥 0~H m. 비스듬히 찍힌 빌라가 정면도처럼 반듯해진다. 1 m 격자와 층 선을 그리면 그것이 "밑에 깐 그림"이다.
3. 펼친 정면 위에서 조각(사각형)을 자른다. 조각 하나 = 부품 하나. `_wall_part(along, y_m, out, size)`가 "면 위 어디에, 어느 높이에, 얼마나 튀어나와, 어떤 크기"로 부품을 놓는 함수라 그대로 호출한다. 튀어나오는 깊이만 종류별 기본값.
4. 만든 뒤 같은 카메라로 Studio를 캡처해 같은 호모그래피로 펼치고 사진 위에 겹쳐 어긋남을 본다.

오차의 원천은 카메라 자세다(파노라마 위치 1~2 m, heading, 카메라 높이 가정 2.5 m, 지형). G3 윤곽선이 몇 픽셀 어긋나는 이유와 같다. 해결은 에이전트가 사진에서 정면 네 모서리를 찍어 주는 것(3단계 보정)이고, 그러면 자세 오차와 무관하게 펴진다.

해상도: 20 m 거리·가로 시야각 100°면 약 21 px/m. 창(1.5 m ≈ 32 px)·계단탑·대문·발코니는 충분하고 창살·줄눈은 안 된다(재질로 둔다).

## 3. 대상

사용자가 보여 준 묶음 이미지의 빌라 둘과 같은 종류로 2~4동. 1급 칸(6d3 또는 다음 칸)에서 `uv run src/details.py list --cells <칸> | grep "finish=brick" | grep "stair=glass"`로 후보를 뽑고, 묶음(`captures/<칸>/sheets/gis_N.jpg`)에서 정면이 나무·차에 덜 가린 것을 고른다. 사용자가 보여 준 둘의 생김새(찾는 데 참고):

- A: 3층 적벽돌 빌라. 가운데 전 층 유리 계단탑(청록), 그 오른쪽에 곡면 유리 돌출창 스택(크롬 틀), 왼쪽 측면에 돌(잡석) 외장, 기와 지붕 대문 + 벽돌 담 위 철 난간, 1층 앞 화단.
- B: 3층 + 옥탑 적벽돌 빌라. 왼쪽 끝 둥근 곡면 창 스택, 가운데 유리 계단탑, 옥상 유리방·난간, 벽돌 원기둥 대문 기둥 + 금색 장식 철문.

## 4. 절차

### 4-1. 펼치기 도구 `src/facade.py` (새 파일, 표준 라이브러리 + numpy + Pillow, `lookalike`·`layout_details`·`review` 재사용)

```
uv run src/facade.py unfold --cells <칸> --building gis:N [--rank 1] [--corners "x,y x,y x,y x,y" [--top-m 10.2]]
  → data/facade/<칸>/gis_N__<rank>.jpg   펼친 정면 + 1 m 격자(층 선은 굵게) + 축 눈금(m)
  → data/facade/<칸>/gis_N__<rank>.outline.jpg   원본 크롭에 박스 정면 네 모서리와 윤곽선을 자홍으로 겹친 것(모서리 보정용)
  → data/facade/<칸>/gis_N__<rank>.json   {face side, L_m, H_m, fh_m, floors, t_sign, px_per_m, H(3x3), corners_px, source crop}
uv run src/facade.py measure --cells <칸> --file <조각 JSON>     # 조각마다 펼친 사진에서 색을 재서 rgb_measured를 채우고 regions/<구역>/cells/<칸>/facade.json으로 합친다
uv run src/facade.py compare --cells <칸> --building gis:N --capture <Studio 캡처.png>
  → data/facade/<칸>/gis_N__compare.jpg   왼쪽 사진 펼침 / 가운데 렌더 펼침 / 오른쪽 50% 겹침, 조각 사각형을 선으로 표시
```

구현 메모:
- 입력: `review.json`에서 그 건물의 pair(카메라, `crop`, `label.floors`, `label.height_m`), `chunks.json`에서 그 건물의 `k=building` 항목(여러 박스면 카메라에 가장 가까운 박스; 박스 바닥 y = 항목 y − h/2, 땅 높이가 이미 들어 있다).
- 정면 고르기: `lookalike.faces_toward`로 카메라를 향한 면들 중 투영 다각형 넓이가 가장 큰 면. `--rank`를 안 주면 세 크롭 중 그 면의 투영 넓이 × (사진 안에 들어온 비율)이 가장 큰 크롭.
- 면 좌표: `layout_details.face_of(box, side)`의 중심 c·접선 t·법선 n(m). 면의 두 끝 c ± t·L/2를 사진에 투영해 **사진에서 왼쪽에 보이는 끝을 u = 0**으로 삼고 `t_sign`(+1이면 u가 t 방향, −1이면 반대)을 JSON에 적는다. 생성기는 `along = t_sign × (u − L/2)`로 바꾼다.
- 호모그래피: 펼친 그림 픽셀 (u·s, (H − y)·s) ↔ 사진 픽셀. 4점 DLT(numpy). Pillow `Image.transform(size, Image.PERSPECTIVE, coeffs, Image.BICUBIC)`는 출력 → 입력 방향 계수 8개를 받으므로 "펼친 그림 → 사진" 행렬을 H[2,2] = 1로 나눠 넘기면 된다. `px_per_m`은 40(12 m 면이면 480 px).
- `--corners`: 에이전트가 `.outline.jpg`를 보고 윤곽선이 어긋났을 때 사진 픽셀로 준 정면 네 모서리(왼쪽 아래, 오른쪽 아래, 오른쪽 위, 왼쪽 위 순, 사진에서 보이는 대로). 위가 잘렸으면 `--top-m`으로 "이 네 점의 위쪽은 바닥에서 몇 m인가"(예: 3층 바닥 선이면 3 × fh)를 준다. 주면 박스 투영 대신 이 네 점으로 편다.
- 테스트(`tests/test_facade.py`): 합성 카메라와 상자로 정면 네 모서리를 투영 → 펼침 → 다시 투영하면 원래 픽셀(왕복 1 px 이내); `t_sign`이 카메라를 면의 양쪽에 두었을 때 뒤집힘; 조각 → `_wall_part` 항목의 중심이 u·y와 맞음; 조각이 면 밖(u < 0, u1 > L, y1 > H + 옥탑 허용)이면 거부.

### 4-2. 조각 적기 (에이전트, 눈가림)

에이전트에게 주는 것: 펼친 정면 `gis_N__<rank>.jpg` 하나(필요하면 `.outline.jpg`와 원본 크롭도 보정용으로). 렌더·DB·details·규칙 코드는 보지 않는다. 출력은 건물마다 아래 JSON 한 덩어리.

```json
{"building_id": "gis:N", "rank": 1,
 "corners_px": null,
 "pieces": [
  {"kind": "glass_stair", "u0": 5.5, "u1": 6.5, "y0": 0.0, "y1": 10.2},
  {"kind": "bay_curved",  "u0": 1.0, "u1": 3.5, "y0": 3.4, "y1": 10.2},
  {"kind": "window",      "u0": 7.1, "u1": 8.6, "y0": 4.4, "y1": 5.9},
  {"kind": "window",      "u0": 7.1, "u1": 8.6, "y0": 7.8, "y1": 9.3},
  {"kind": "gate_tiled",  "u0": 0.0, "u1": 2.5, "y0": 0.0, "y1": 2.4, "out_m": 4.0},
  {"kind": "fence_brick", "u0": 2.5, "u1": 12.0, "y0": 0.0, "y1": 1.2, "out_m": 4.0},
  {"kind": "stone_base",  "u0": 0.0, "u1": 12.0, "y0": 0.0, "y1": 0.6}
 ],
 "occluded": [{"u0": 8.0, "u1": 12.0, "y0": 0.0, "y1": 6.0}],
 "note": "short English, no people, plates, brands"}
```

- 좌표는 m. u는 펼친 그림 왼쪽 끝이 0, y는 바닥이 0(격자 눈금 그대로). 층 선을 기준으로 읽으면 쉽다.
- 종류와 기본 깊이(m, 면에서 바깥으로):

| kind | 뜻 | 깊이·모양 |
|---|---|---|
| `window` | 창 하나(유리 + 틀) | 틀 0.08 밖, 유리 0.05 |
| `glass_stair` | 유리 계단탑 | 0.3, 유리색 |
| `brick_stair` | 벽 재질 돌출 계단실 | 0.6, 벽 색 |
| `round_stair` | 원형 계단탑 | 지름 = u1 − u0의 원통 |
| `bay` / `bay_curved` | 각진 / 곡면 돌출창 스택 | 1.2; 곡면은 원통 반쪽(또는 3조각) |
| `balcony_open` / `balcony_glazed` | 열린 난간 / 유리로 막은 발코니(층마다 한 조각) | 1.5 (바닥판 + 난간 또는 유리) |
| `door`, `shopfront`, `awning`, `sign`, `ac_unit` | 문, 가게 유리, 차양, 간판, 실외기 | 0.05 / 0.05 / 1.2 / 0.1 / 0.3 |
| `gate`, `gate_tiled`, `fence_brick`, `fence_iron` | 대문, 기와 지붕 대문, 벽돌 담, 철 담 | `out_m`(면에서 담까지 거리) 필수. 기와 대문은 위에 0.6 m 쐐기 지붕 |
| `stone_base`, `band`, `panel` | 기단 석재, 띠, 다른 색 판(두 가지 색 벽) | 0.05 / 0.08 / 0.03, 색은 측정 |
| `rooftop_box`, `roof_railing` | 옥탑(y가 H 위), 옥상 난간 | 옥탑은 `d_m`(기본 3), 난간 0.05 |

- 색은 에이전트가 적지 않는다. `facade.py measure`가 조각 안쪽 60 % 영역의 중앙값(occluded와 겹치는 부분 제외)을 `rgb_measured`로 채우고, 조각이 덮지 않은 나머지 벽에서 벽 색을 재서 `wall_rgb`로 둔다(`walls.json`과 같은 방법, 사진에서 잰 색을 쓰는 것은 2026-10-17 사용자 결정으로 허용됨).
- 가린 곳(`occluded`)은 조각을 적지 않고 비워 둔다. 생성기는 그 자리를 지금 규칙(창 열)으로 채운다.
- 한 에이전트에 이미지 20장 안팎(요청 한도 교훈, lessons 2026-10-17 61b).

### 4-3. 생성

- `build_luau.py`가 `common.cell_file(cfg, cell, "facade")`로 `facade.json`을 읽는다(`walls.json`과 같은 자리·같은 방식, 없으면 아무 변화 없음).
- 트레이싱된 몸체는 **그 면만** `_villa_face`·`front_items`(계단탑·돌출창·발코니·문) 대신 `facade_items(pieces)`로 만든다: `along = t_sign × ((u0 + u1) / 2 − L / 2)`, `y_m = y0`, `size = (u1 − u0, y1 − y0, 깊이)`, `out = out_m`(기본 0). 다른 면·층 띠·지붕·옥상·간판·마당 규칙은 그대로. 담·대문 조각이 있으면 `yard_items`의 담·대문은 그 건물만 끈다.
- 결정성: 조각은 파일에서 오니 같은 입력 → 같은 덩어리(BR-14.8 유지). 조각 항목 이름은 `<건물>#tp<번호>`로 SAFE_TEXT 안.
- Studio: 그 칸을 `unpack.luau`로 꺼내고 → `build_luau.py --cells <칸>` → `studio-build.luau`로 칸 다시 생성(cycle-build 6단계 그대로, 바뀌는 건 트레이싱한 2~4동뿐) → 확인 끝나면 `pack.luau`(cycle-build 5c).

### 4-4. 겹쳐 보기

- Studio 시야각 83.58, `screen_capture`에 `review.json` pair의 `camera_position`·`look_at_position`을 그대로(한 번에 하나씩). 창은 4:3보다 넓게.
- `facade.py compare`가 캡처를 `review.capture_crop_box`로 크롭 각도에 맞게 잘라 **박스 투영 호모그래피**(렌더는 정확히 박스이므로 보정 없이)로 펼치고, 사진 펼침(보정했으면 보정된 것)과 나란히 + 50 % 겹침을 만든다. 조각 사각형을 선으로 그려 사진의 그 요소와 얼마나 어긋나는지 본다.
- 같은 캡처와 크롭으로 `lookalike.py`식 쌍(왼쪽 사진, 오른쪽 렌더)도 한 장 만들어 `cell-score`(`lookalike-rubric.md`)에 채점시킨다. 비교 기준은 같은 건물의 **지금 규칙 렌더**(바꾸기 전 캡처를 먼저 떠 둔다).

## 5. 성공 기준과 적을 것

| 항목 | 기준 |
|---|---|
| 조각 위치 | 겹침에서 계단탑·돌출창·창·대문의 가장자리 어긋남 0.5 m 이하(40 px/m면 20 px) |
| 닮음 | `cell-score` 총점 12점 중 10 이상, `same_building: true`, 2~4동 모두. 같은 건물의 규칙 렌더 점수와 나란히 적는다 |
| 부품 | 트레이싱한 건물의 부품 수가 규칙판의 1.5배 이하 |
| 모서리 보정 | 네 모서리 보정이 필요했는지, 몇 px(몇 m)이었는지, 에이전트가 픽셀 좌표를 믿을 만하게 주는지 |
| 비용·시간 | 건물 하나당 에이전트 토큰·시간(판단 $3/칸, 채점 $9/칸과 비교) |
| 가림 | 세 크롭 중 쓸 만한 정면이 있었는지, 없는 건물 비율 |

결과는 `aidlc-docs/lessons.md`에 날짜·칸과 함께, 비교 이미지는 `data/facade/`(git 제외)에, 사용자 입력은 `audit.md`에. 사용자가 결과 이미지를 보고 판단한다.

## 6. 하지 않는 것

- 사진을 텍스처로 쓰지 않는다(2026-10-12 결정 그대로). 조각은 부품이고 색만 사진에서 잰다.
- 사진·펼친 그림을 Roblox에 올리지 않고 git에 넣지 않는다(`data/`·`captures/`는 이미 git 제외). git에는 `facade.json`(좌표·색·짧은 메모)만. 메모에 사람·번호판·상호 없음.
- 7필드 판단, G3 게이트, `gate.toml`, U8 큐·에이전트는 바꾸지 않는다. 실험이 끝나고 사용자가 결정하면 유닛으로.
- 가림 자동 감지, 모서리 자동 맞춤(에지 스냅), 옆면·뒷면 트레이싱은 이번 범위 밖(되면 다음에).

## 7. 성공하면 정할 것 (사용자 결정, 질문 파일로)

1. 범위: 1급 칸의 사진 있는 건물 전부인가, 빌라·상가만인가. 2·3급은 지금 규칙 유지.
2. 이미 만든 82칸: 다시 트레이싱해서 다시 만들 것인가(묶음·크롭은 로컬에 있어 재판단은 가능. 판단 $3/칸 기준으로 2~3배 추정), 새 칸부터인가.
3. 7필드 판단과 메모를 남길 것인가(트레이싱 못 한 면·가린 자리의 기본값으로만 쓰는 안).
4. G3 채점자의 `rule` 항목 `want`를 자유 문장 대신 고정 목록으로 바꿀 것인가(지금은 문장이 달라 `gaps --min 10`에 쌓이지 않음).
5. 자동 확장(U8) 에이전트에 트레이싱 단계를 어디에 넣을 것인가(`cell-judge` 대신 또는 그 뒤).
