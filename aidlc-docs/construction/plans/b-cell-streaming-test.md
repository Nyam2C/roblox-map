# B 시험: 서버가 근처 칸만 만들기 (2026-10-15)

사용자 결정(2026-10-15, place-split-questions Q1 = C): B를 먼저 시험하고, 안 되면 A(장소 약 100칸씩).

## 방법
Studio Play의 서버에서만 했다. 서버 쪽 복사본이라 저장되지 않는다. 스크립트는 `b-cell-streaming-test.luau`.
- 25칸의 `chunks.json`을 127.0.0.1에서 한 번 받아 zstd로 압축해 메모리에 둔다(장소 안에 넣어 둘 데이터의 대역).
- 서버의 `Workspace/Auto`를 비운다.
- 0.5초마다 플레이어에서 칸 중심까지 거리를 본다. 1,500 stud 안이면 만들고, 2,000 stud 밖이면 지운다. 칸은 한 번에 하나씩, 덩어리 하나를 만들 때마다 프레임을 넘긴다.
- 캐릭터는 서버에서 초당 42 stud(킥보드 속도)로 037 → 1cb → 1c7 → 113 → 117 → 1ab → 133을 162초 동안 달리고, 같은 길로 돌아온다.

## 결과
| 항목 | 결과 |
|---|---|
| 압축 | 칸 하나 1.69 MB → 116 KB(zstd 9). 풀기 0.7 ms, JSON 읽기 6~10 ms. 752칸이면 약 87 MB |
| 칸 하나 만들기 | 72~125덩어리, 1.2~3.5초(덩어리마다 프레임 넘김). 덩어리 하나는 최대 21 ms |
| 칸 하나 지우기 | 최대 0.22초(모델 하나씩, 2 ms 넘으면 프레임 넘김). 지우기 한 번은 최대 11 ms |
| 동시에 있는 칸 | 플레이어 1명에 3~7칸. 메모리는 칸 수에 따라 오르내리고, 지운 칸 몫은 돌아왔다 |
| 클라이언트 FPS | 가는 길: 대부분 60, **985 ms 멈춤 한 번**(서버 heartbeat에도 같은 시각에 985 ms). 오는 길: 158초 평균 59.9, 1초 최저 55.6, 50 ms 넘는 프레임 2개(57·55 ms) |
| 서버 heartbeat | 오는 길: 33 ms 넘는 프레임은 칸 폴더가 생기거나 지워지는 순간뿐(34~64 ms) |

985 ms 멈춤은 한 번만 나왔다. 오는 길에는 같은 칸들을 다시 만들고 지웠는데도 나오지 않았다. 원인(첫 로딩, GC 등)은 아직 모른다.

## 판단
되는 방식이다. 플레이어 1명이 쓰는 서버 부품은 7칸 × 약 9천 = 약 6만 3천 개(약 0.4 GB)다. 서버 한도(약 80만 부품)면 서로 떨어진 플레이어 약 11명까지, 근처에 모이면 더 된다.

## B로 가려면 남은 일
1. **먼 경치**: 먼 칸은 아예 없으니 스카이라인이 사라진다. 부천 전체를 "건물 상자만" 넣은 가벼운 판으로 깔아 두면 해결된다(칸당 약 100~200부품, 752칸이면 약 11만 개). 가까운 칸이 만들어지면 그 칸의 상자는 숨긴다.
2. **데이터 넣기**: 압축 데이터 87 MB를 장소 안 어디에 둘지 정한다(문자열 값·모듈·DataStore). 저장했다가 다시 열어 보는 시험은 사용자 저장이 필요하다.
3. **정식 스크립트**: 가까운 칸부터 만들기, 여러 플레이어, 칸을 만들고 지울 때의 순간 비용(34~64 ms) 줄이기, 985 ms 멈춤 재현.
4. **순간 이동**: 지도에서 먼 칸으로 갈 때는 그 칸을 먼저 만들고 보낸다(2~4초 로딩 화면).
5. **수작업 시설**: `Manual`도 칸에 붙여 같이 불러오고 지운다. 지금 25칸에만 2만 6천 개다.
6. **플레이어 수**: 서버 최대 인원을 정한다(흩어지면 1명당 약 0.4 GB).
